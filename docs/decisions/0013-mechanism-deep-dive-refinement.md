# ADR-0013：产品叙事收窄为"机制级深挖"；两阶段交互；措辞纪律；验证边界

**状态：** 已接受（2026-07-03）

## 决策

在 [ADR-0012](./0012-product-niche-alt-research.md) 基础上，进一步收窄和澄清四件事：

1. **核心增量重新定位**：不是"调研某产品有哪些开源平替"（这一层 GitHub Topics 聚合页 + 博客 listicle 已经免费覆盖），而是**用户带着一个具体机制疑问进来（"Cluely 怎么做到反截屏不被录进去的"），agent 去几个开源平替的源码里交叉验证这个机制怎么实现**。前者是信息检索，后者才是尽调。
2. **两阶段交互模型**：Stage 1（广度概览：这个产品有哪些开源平替、各自主打什么）→ 用户挑一个具体机制 → Stage 2（深度挖掘：3+ 个开源实现的源码交叉印证该机制）。这不是一次性生成报告，是"报告 → 追问 → 深挖"的多轮对话。
3. **报告措辞纪律**：agent 能证明"开源社区怎么实现这个效果"（读得到代码），**不能**证明"闭源产品内部怎么实现"（没有源码，永远不可得）。报告输出必须严格区分这两句话，不能因为交叉印证结果一致就偷换成对闭源产品的断言。
4. **验证边界从"P1 待排期"改为"架构性不做"**：GUI/OS 级行为验证（如 macOS 专属的屏幕录制检测实测）在当前执行模型（agent-in-sandbox 跑在云端 headless 容器）下**不是"暂时没做"，是"这个架构永远做不到"**。应写入 PRD 非目标清单，不再挂在 P1 画饼。

## 背景

拷问 [ADR-0012](./0012-product-niche-alt-research.md) 的"三刀"论证时，先用真实检索验证了"广度刀"的假设：`github.com/topics/cluely-alternative` 这个 Topics 页，以及至少一篇现成博客 listicle（shadecoder《Top 10 Cluely Alternatives》），已经把 Pluely / OpenCluely / Open-Cluely / Natively 这类平替聚合并做了功能对比。这说明"全网搜 + 列出平替 + 列功能对比"这一层本身**不构成差异化**，纯粹是信息聚合，别人已经免费做过。

真正的差异化线索来自用户自己回忆调研 Cluely 平替的真实动机：不是想知道"有哪些平替"，是想知道"Cluely 最黑科技的那个功能（投屏不被录进去）具体是怎么实现的"。这是机制级问题，topic 页/listicle 答不了，因为它们只总结"是什么"，不深入"怎么做到"。

## 连带澄清的三个问题

**受众**：产品经理/运营/开发者中，已经用过或见过某个 AI 产品、被某个具体功能"惊到"的人——不是不知道产品存在的小白。这批人问的是"怎么做到的"，不是"有没有平替"。

**验证对象的逻辑边界**：Cluely 闭源，agent 永远读不到它的源码，因此永远无法验证"Cluely 内部到底调了什么 API"——这与执行环境（云端/本地/沙箱）无关，是信息不可得，不是能力不够。agent 能做的唯一动作是读取**开源平替**的源码，如果 3 个独立项目都调用了同一个系统 API（如 `WDA_EXCLUDEFROMCAPTURE`），可以有把握地说"开源社区是这么复现这个效果的"，但不能说"Cluely 是这么做的"。

**频次**：低频、事件驱动型使用（用户被某个功能"惊到"的那个瞬间才会打开），不追求留存曲线。这与 [ADR-0012](./0012-product-niche-alt-research.md) 背景中"作者是重度用户/工程作品集优先"的定位一致，不需要额外设计召回机制。

## 被否/被纠正的表述

- ~~"三刀"里的"广度：全网捞 GitHub/HN/Reddit/博客，交叉验证"~~ —— 这一层已被现成聚合页覆盖，不能算作差异化论证的主力，面试被追问时不能拿这条当王牌。
- ~~"验证类能力推到 P1，需要时再加"~~ —— 对 GUI/OS 级行为验证不准确，这类验证在当前架构下不是"以后可以加"，是"结构性做不到"，必须改口为非目标，否则面试官会问"那你 P1 打算怎么加",答不上来。

## 连锁影响

- **PRD**：补一节"非目标"，写明 GUI/OS 级行为验证不在能力范围内（架构原因，非排期原因）。
- **agent-runtime-protocol.md / 报告输出规范**：需要一条硬性措辞规则——"开源实现描述" vs "闭源产品断言"必须可区分（例如报告模板里对闭源目标产品的机制描述统一加"（据其官方描述/据交叉验证的开源实现推断）"这类限定语，不能写成确定性陈述）。
- **交互模型**：产品主路径从"单轮报告生成"变为"Stage 1 概览 → 用户选择 → Stage 2 深挖"的多轮对话，这把 [OPEN-QUESTIONS.md](./OPEN-QUESTIONS.md) 的 **DQ-1（`waiting_for_input` 状态）** 从边缘 case 提升为主交互路径的地基——DQ-1 不再是"human-in-the-loop 万一用到"的兜底设计，是每次调研都会走到的必经状态。DQ-1 的钻取优先级应提前。
- **术语表**：可能需要补"机制深挖（Mechanism Deep-Dive）""Stage 1/Stage 2"等新术语。
- **ADR-0012 三刀论证**：不废弃，但第 1 刀（广度）的分量在面试话术里应降权，第 2 刀（深度/机制验证）应升级为主论点，并补上本 ADR 的"两阶段交互"作为具体落地机制。
