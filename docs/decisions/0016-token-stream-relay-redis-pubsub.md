# ADR-0016：Token 流跨实例转发——引入 Redis Pub/Sub，解决 DQ-2

**状态：** 已接受（2026-07-03）

## 决策

解决 [OPEN-QUESTIONS DQ-2](./OPEN-QUESTIONS.md)：token 级实时流（thinking/说话逐字直通）**引入 Redis pub/sub 作为跨实例转发层**，不采用"P0 先降级为只做业务事件流"的退路（DQ-2 选项 A），也不采用"轮询 DB 近似实时"（DQ-2 选项 B）。

核心问题不是"要不要攒批"（**不攒批，这条已确定**：token 流转发路径上任何一环都不允许积累一段再发，必须逐 token 立即转发），而是**沙箱所在的处理实例和前端 SSE 所在的处理实例，是两个不共享内存的独立进程**（生产环境下，甚至可能是不同物理机器；即便同机，Vercel serverless 函数每次调用也可能是不同实例）。两个不共享内存的进程之间要实时互相通知，必须有一个双方都能访问的外部中介，数据库不适合承担这个角色（数据库是持久化存储，为"读多写少、追求一致性"设计；这里的需求是"高频、易失、要求毫秒级广播"，用轮询数据库模拟只会锁死延迟在轮询间隔上，且轮询会比正常业务查询更快打满数据库连接）。

流程：

```
1. 沙箱收到 LLM 吐出的一个 token
2. 沙箱调用后端一个新端点（如 POST /api/ingest/stream-chunk），
   该端点内部把这个 token"发布"（PUBLISH）到 Redis 的一个频道（按 runId 区分，如 "run:{runId}"）
   —— 这个端点不写数据库，只做发布，是内存级操作，毫秒级
3. Redis 立刻把这条消息广播给所有"订阅"（SUBSCRIBE）了这个频道的人
4. 处理前端 SSE 请求的那个后端函数实例，在这次 SSE 连接期间订阅对应 runId 的频道
5. 该实例收到 Redis 广播的消息，立刻写入 SSE 响应流，前端收到
```

Redis pub/sub 不持久化消息——如果发布那一刻没有订阅者在听，这条消息就丢了，Redis 不会替你留着。这与 [ADR-0011](./0011-dual-channel-streaming.md) 已经定的"token 流可重放可丢，丢几个不影响正确性"完全吻合：真正的事实源仍然是"语义单元完整时（如 `TEXT_MESSAGE_END`）落库一整段"这条独立路径，token 转发路径全程不落库，两条路径解耦、互不阻塞。

工具调用（tool_call_started/completed）、file_written、artifact_created 等业务事实**不走这条 pub/sub 转发路径**——它们本身是一次性的完整对象（不是逐字流），继续走 [ADR-0011](./0011-dual-channel-streaming.md) 已定的"先落库、确认成功后再广播"的可靠通道（现有 ingest API），不受本 ADR 影响。

## 背景

这个问题在架构讨论里反复被绕过去，直到被逼问"生产环境前端的请求和 sandbox 的请求打到不同机器上，还没落库呢，怎么转发这个 SSE 流"才被精确提出。核实结果：这是业界一个有专门名字的通用问题（multi-instance broadcast problem / 水平扩展下的实时消息路由问题），凡是"实时消息"功能一旦不再局限于单进程/单机器就必然撞上，与 SSE/WebSocket/Socket.io 等具体协议无关。业界标准解法高度一致：引入一个所有实例都能访问的外部 pub/sub broker（最主流是 Redis），不存在"纯数据库"或"纯 serverless 内存"的替代解法。参考：Socket.io 官方文档、多篇 SSE/WebSocket 分布式广播实践文章均确认这一点（结论来自实测搜索验证，非凭空推断）。

DQ-2 原本"倾向"是 P0 先做选项 A（降级为只做业务事件流），token 级流式留作 P1 用选项 C（Redis 或等价中间层）解决。本 ADR 把这个决定提前——直接在解决方案层面把选项 C 钉死，不再悬着。是否在 P0 就实现，还是先记录方案、P0 仍走 A 降级、P1 再实现 C，是本 ADR 未覆盖的排期问题（见下）。

## 被否方案

- **DQ-2 选项 B（前端轮询 DB 最新 token 段近似实时）：** 延迟锁定在轮询间隔上，且轮询本身会比正常业务查询更快打满数据库连接（呼应 [ADR-0015](./0015-usage-telemetry-and-ops-priorities.md) 已知但推后的连接池问题——用轮询模拟实时反而会提前触发那个问题）。
- **用一张临时的 Postgres 表模拟消息队列（每个 chunk insert 一行，另一端轮询读表）：** 讨论过程中一度提出又被否——这是拿持久化存储去扛高频、易失的转发场景，本质和"轮询 DB"是同一类错误，只是换了张表。数据库不是消息总线，不该承担这个角色。
- **P0 就此放弃 token 级实时，只做业务事件流（DQ-2 选项 A）：** 未被彻底否决，是本 ADR 未决定的排期问题——技术方案已经证明"token 级实时在纯 Vercel 架构下是可行的、有标准解法的"，不再是"做不到"，只是"要不要现在做"变成了单纯的优先级/工程量取舍，不再是技术不可行导致的降级。

## 未覆盖、留给实现阶段的问题

- **Vercel serverless 函数处理 SSE 连接时，能不能长时间维持 Redis 订阅状态直到 run 结束：** 本 ADR 解决的是"两个不同实例之间怎么互相通知"，不解决"单个函数实例最多能存活多久"（仍是 300s 上限问题）。这两个问题分开处理——后者仍需要 EventSource 自动重连 + `Last-Event-ID` 的机制（此前讨论提过，尚未正式落 ADR）。
- **Redis 的具体接入形态**（自建 Redis / 托管服务如 Upstash / Vercel KV 等）未选型，留给实现阶段按成本和 Vercel 生态集成度决定。
- **P0 是否真的要做 token 级实时，还是继续走 DQ-2 选项 A 的降级路线，把本 ADR 的方案留到 P1 再实现**——这是产品优先级判断，不是本 ADR 的技术结论，需要用户单独拍板。

## 连锁影响

- **依赖新增基础设施：** Redis（或等价 pub/sub 服务）成为 P0/P1（视上一节排期决定）的新增外部依赖，需要在部署清单和环境变量清单中补充。
- **agent-runtime-protocol.md：** 需要新增一节，定义沙箱调用的 `POST /api/ingest/stream-chunk`（或类似命名）端点契约——不同于现有 `POST /api/ingest/events`（该端点用于落库的业务事实/聚合语义单元），这个新端点专门用于逐 token 发布、不落库。
- **api-contract.md：** SSE 端点（`GET /api/runs/:runId/events`）的实现需要新增"订阅 Redis 频道并转发"这一层逻辑；事件类型列表可能需要区分"来自 Redis 转发的高频 token 事件"和"来自 DB 查询/推送的业务事实事件"。
- **OPEN-QUESTIONS.md：** DQ-2 可以从"待决"移除，改为已解决并链接本 ADR；但上一节列的三个未覆盖问题（SSE 连接存活时长、Redis 选型、P0 排期）如果需要继续跟踪，应作为新的 DQ 或直接留在本 ADR 的"未覆盖问题"里，不必再单独开一条 DQ。
