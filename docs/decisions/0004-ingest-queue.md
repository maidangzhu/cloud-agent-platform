# ADR-0004：Ingest 采用超薄同步写库 P0 形态，按可插队列的管线分层

**状态：** 已接受（2026-07-02）

## 决策

- **P0：** ingest API 直接同步写库（验 token → 校验 → 写 Postgres），不引入队列。
- **分层要求：** ingest handler 写成一条清晰管线（验 token → 校验 → 持久化），使"持久化"这一步未来可无痛替换为"入队 + 异步消费"。
- **P1（队列削峰）：** 触发条件为并发压测到 Postgres 成为写入瓶颈。届时在 **ingest API 背后**（可信区内部）插入队列，消费者匀速落库。

## 背景

目标是"同时 50 个 run 不挂"。在 Agent-in-Sandbox 架构下：

- 50 个 run = 50 个独立 microVM 各自跑 agent loop，**重活（LLM 推理、跑命令、抓网页）全压在沙箱，不碰 Control Plane**。
- Control Plane 在这期间只做两类又短又轻的活：点火（几秒）、接 ingest 报文（每次几毫秒写库）。
- 因此 Control Plane 不会因"算得多"而挂，只可能因**写库尖峰**而挂（50 沙箱疯狂回报 ≈ 数百写/秒砸 Postgres）。

队列防两件事：①**削峰**（缓冲写库尖峰）；②**不丢**（ingest 端瞬时挂时消息留在队列）。

## 与他人架构的关键差异

参考的某企业架构中，agent（沙箱）**直连 Redis** 自己入队——因为其沙箱与数据同处一信任区。

**本项目不同：** 沙箱是不可信区（[ADR-0001](./0001-execution-model.md)），铁律是沙箱不持任何后端凭证，DB/Redis 连接串都不给。因此队列必须坐在 ingest API **背后**，沙箱永远只说 HTTP：

```
沙箱 runner --HTTP + run token--> ingest API（超薄：验token → 塞队列 → 立刻 200）
                                        |
                                        v
                                   队列（内部，可信区）
                                        |
                                        v
                                  消费者 worker --> Postgres
```

## 被否方案

- **P0 就上 Redis：** 过早优化，拖慢核心架构验证（首要目标是证明 agent 真在沙箱跑、事实经 ingest 回流），且"企业都这么干"不是理由。
- **沙箱直连队列（照抄参考架构）：** 破坏信任边界，沙箱不得持后端凭证。

## 连锁影响

- 面试叙事：P0 直接写库验证正确性 → 压测到瓶颈 → 引入队列把写入从同步改异步。有数据、有演进、有权衡。
- 队列引入后与事件 seq 顺序的冲突，见 [ADR-0006](./0006-event-seq-at-source.md)。
