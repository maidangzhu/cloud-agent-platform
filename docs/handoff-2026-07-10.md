# 交接说明 — 2026-07-10

给接手 `cloud-agent-platform` 的同事看的。目的：不用重新问一遍"这是什么项目""现在做到哪了"，直接从这里接着做。

## 1. 项目是什么

一个云端 agent 研究平台：用户在 workspace/thread 里发起一个 run，后端在真实 Vercel Sandbox 里启动 Pi AI runtime（`@earendil-works/pi-agent-core` + `@earendil-works/pi-ai`），跑一个 LLM 驱动的 agent loop，通过工具（`read_file`/`write_file`/`run_command`/`web_search`/`fetch_url`/`create_artifact`）读写 workspace 文件、执行命令、生成 artifact，全程通过 ingest API 把状态/事件回写到 Control Plane，前端通过 SSE 实时看到。

技术栈：pnpm monorepo，`apps/api`（Hono，独立部署）+ `apps/web`（Next.js）+ `packages/db`（Prisma + Neon Postgres）。Redis（Upstash）用于 token 流式转发。已经部署到 `https://api.sandbox.maidang.me`，能跑通端到端真实链路。

## 2. 现在处于什么阶段

**不是"继续赶完整链路"，是"架构分层测试收敛"阶段。** 端到端已经能跑（`test:live` 全绿），但过程中发现底层模块的测试覆盖有真实缺口——不是"少写了几个 case"，是复核时直接测出了生产代码里的并发 bug。所以现在的原则是：从最底层的模块开始，一层一层把测试补扎实、把代码读透，再往上走，不要用"完整链路能跑"来掩盖模块本身没测过的问题。

## 3. 这一轮（2026-07-10）具体做了什么

### 3.1 Control Plane 是什么，为什么不能跟 Sandbox/Redis 合并

如果你也有"Control Plane 好像什么都装、边界不清楚"的困惑：它不是 CRUD 层，是**唯一事实源 + 状态机 + 安全代理**这三件事的合集，只有它能碰业务数据库。之所以要和 Sandbox（不可信执行环境）、Redis（故意设计成可丢失的瞬时通道）、Workspace Mapping（DB 事实 vs 沙箱磁盘的同步边界）分开，是因为这几层的"数据可信度、持久性、失败恢复方式"完全不同，混在一起测会分不清一个失败是模块内问题还是黑盒问题。类比 Kubernetes 的 control plane vs data plane。

### 3.2 完成了 CP-* case 到具体测试文件的映射

`architecture-test-plan.md` §4.3 每个 CP-* case 现在都标了对应的测试文件和 `it()` 名字，不再是"标了 existing 但不知道具体哪个测试覆盖"的状态。

### 3.3 复核并发安全时发现并修复了 3 个真实 bug

方法论：不满足于"existing 测试都是绿的"，专门去补**真正的并发测试**（用 `Promise.all` 同时发起两个请求，而不是串行调用两次），因为很多"先查后写"式代码在串行测试下看不出问题，只有真并发才会暴露竞态。这次一共揪出了 3 个：

1. **Event Store（`apps/api/src/run/event-store.ts`）**：
   - `insertRunEvent` 里 `maxSeq` 边界判断用了 `<=` 应该是 `<`，导致并发下同 seq 同内容的合法重试会被误判成 `INGEST_SEQ_CONFLICT`。
   - `isUniqueConstraintError` 用 `isPlainObject` 判断 Prisma 抛出的异常，但真实的 `PrismaClientKnownRequestError` 是类实例、永远不是"字面量对象"，导致这个 catch 分支从未真正生效——并发写撞数据库唯一约束时，异常会直接抛出到调用方。
   - 已修复，`isUniqueConstraintError` 现在 export 了，供其他模块复用。

2. **RunToolCall 状态转移（`apps/api/src/ingest/routes.ts` 的 `/api/ingest/tool-calls`）**：
   - 最严重的一个。`existing -> update` 分支只用 `{ id: existing.id }` 做 `where`，没有带上"当前状态必须还是我刚读到的那个"这个条件（对比 `transitionRun` 的条件 UPDATE 模式）。两个并发的终态上报（比如同一个 `run_command` 调用，一个说 completed、一个说 failed）会**都返回 200，静默地"最后写入者赢"**，没有任何错误或日志暴露这次数据损坏。已修复：改成 `updateMany` 加状态条件，输的一方返回 409。

3. **Artifact 创建（`createFirstArtifact`）**：
   - 排查后确认：在当前配置下（Pi runtime 工具串行执行、`control-plane-client.ts` 无客户端重试）这个场景**暂时不会被触发**——跟前两个不一样，前两个是活跃的生产 bug。但代码本身没有防御：如果两个并发请求带同一个 client-supplied `artifactId`，第二次 `create()` 会撞主键唯一约束，异常穿透变成 500。已做防御性修复（catch 住返回 409），不等它变成真实故障才修。

### 3.4 一次判断失误，已撤回——务必读一下这段，避免重复踩

复核 `run/create.ts` 时，看到前端 `composer.tsx` 的 `canSubmit` 逻辑禁止"有活跃 run 时提交新 run"，就判断这是后端遗漏的强制规则，改代码加了 `NOT EXISTS` 检查（同一 thread 不能有第二个非终态 run）。**这个判断是错的**：跑测试后 67 个用例失败，一查才发现产品设计本来就允许同一个 thread 内有多个连续 run（ADR-0013 的 Stage1/Stage2 机制深挖模型），`composer.tsx` 那条检查只是防止用户手滑重复点击的 UI 细节，不是数据一致性约束。已经用 `git checkout` 撤回。

**教训**：这是这一轮唯一一次没有先写测试验证现状、就直接改了生产代码的情况，直接导致大范围回归。以后任何"这里好像有缺口"的判断，先补一条测试验证现状，再决定要不要改代码。

## 5. 规矩（Claude Code 在这个仓库的行为约束，人类开发者也适用）

- 每个任务做完停下来，等人工确认，不允许连续做多个不停顿。
- 只有明确检查通过才 commit，不主动提交。
- 改动前先跑测试验证现状，不要凭读代码的印象直接改生产代码（见 3.4 的教训）。
- 每次改动后必须跑：`pnpm --filter @cap/api typecheck`、`pnpm --filter @cap/api test`、`pnpm --filter @cap/api test:integration`（需要 `.env` 里的 `DATABASE_URL`）、`npx @fission-ai/openspec validate <change-name> --type change`、`git diff --check`。
- 不要用"完整链路能跑"代替模块测试——这是这轮返工的核心原因。
